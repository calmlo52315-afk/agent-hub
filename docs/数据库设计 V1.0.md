
1. 设计目标
本阶段数据库设计不追求一次定型，而是为 AgentHub 当前与后续阶段提供稳定的数据边界，支持以下能力：

会话与消息持久化
任务拆解与执行状态追踪
Agent 输出与 Review 结果留痕
Artifact 元数据管理
Replay 与 Metrics 存储
为后续 Gateway / Frontend / 多阶段扩展预留演进空间
2. 设计原则
逻辑模型先行，物理存储后定
主业务数据与运行时辅助数据分离
结构化元数据入库，原始大文件走文件系统/对象存储
回放和指标先轻量，后续按规模升级
所有核心记录都尽量带 task_id / session_id / trace_id 方便追踪
3. 数据分层建议
3.1 主业务数据层
建议未来使用：

PostgreSQL 优先
早期可临时用 SQLite 验证模型
适合存：

会话
消息
任务
任务依赖
Agent 执行记录
Review 记录
Artifact 元数据
Prompt/Spec/规则版本引用
3.2 运行时辅助数据层
当前建议：

SQLite：Replay
JSONL / SQLite：Metrics
内存：锁、状态机临时态、上下文窗口
后续可升级：

Redis：状态同步 / 短期缓存 / 分布式锁
OLAP / 时序库：指标分析
3.3 文件与产物层
建议继续走：

本地文件系统（当前）
后续可升级对象存储
适合存：

artifact 文件
diff 文件
preview 相关产物
replay 附件快照
审核报告导出文件
4. 核心实体设计
4.1 sessions
表示用户的一次会话。

建议字段：

id
title
created_at
updated_at
status
owner_id（如果后续有用户体系）
current_stage
主要作用：

前端会话列表
多轮上下文归属
任务归档入口
4.2 messages
表示会话内的消息，包括用户消息、Agent 消息、系统消息。

建议字段：

id
session_id
task_id（可空）
role：user / system / agent
agent_name（可空）
message_type：text / structured_output / event / diff / artifact_ref
content
payload_json
trace_id
created_at
主要作用：

聊天记录持久化
消息回放
上下文拼接
前端流式展示落地
4.3 tasks
表示系统中的任务实体，是 Orchestrator 调度的核心。

建议字段：

id
session_id
parent_task_id（支持拆解）
goal
status
priority
assigned_agent
retry_count
retry_limit
timeout_seconds
input_summary
output_summary
error_code
error_message
created_at
updated_at
主要作用：

任务拆解
执行状态追踪
Retry/Fallback 基础
看板展示
4.4 task_dependencies
表示任务依赖关系，为后续 DAG 做准备。

建议字段：

id
task_id
depends_on_task_id
dependency_type
主要作用：

子任务依赖管理
DAG 执行顺序计算
面试时体现“可扩展编排能力”
4.5 agent_runs
表示某个 Agent 对某个任务的一次执行。

建议字段：

id
task_id
agent_name
run_index
status
input_payload_json
output_payload_json
validation_passed
failure_type
started_at
finished_at
latency_ms
主要作用：

区分 task 和 agent run
精确记录 retry/fallback
回答“哪个 agent 在哪一步失败了”
4.6 reviews
表示 Review Agent 的审核结果。

建议字段：

id
task_id
agent_run_id
passed
score
issues_json
suggestions_json
created_at
主要作用：

审核留痕
review pass rate 计算
评审结果回放
4.7 artifacts
表示产物元数据，不存产物大文件本体。

建议字段：

id
task_id
artifact_type
name
path
version
summary
metadata_json
created_at
主要作用：

Artifact 面板展示
历史版本管理
与文件系统上的真实文件建立关联
4.8 replay_records
这是当前最接近已实现的表。

建议字段：

id
task_id
record_type：message / event / artifact
agent
event_type
payload_json
ts_ms
created_at
主要作用：

时间线回放
故障复盘
比赛演示材料支撑
4.9 metric_events
如果后续把 JSONL 正式入库，可以抽成此表。

建议字段：

id
task_id
agent
metric
value
unit
tags_json
ts_ms
主要作用：

指标查询
性能分析
成本统计
4.10 rule_versions
可选，但很适合比赛和面试。

建议字段：

id
rule_name
version
path
checksum
created_at
主要作用：

记录当前运行时使用的是哪版规则
便于复现“为什么这次任务会这样执行”
4.11 spec_versions
可选，但也很有价值。

建议字段：

id
spec_name
version
path
checksum
created_at
主要作用：

记录运行时契约版本
保证 replay / validation 对应的 schema 可追溯
5. 当前阶段必须支持的数据库操作
这个部分最重要，因为你现在可以先不定数据库，但要先定“系统要做什么操作”。

5.1 会话相关
创建会话
查询会话列表
查询单个会话详情
更新会话标题/状态
获取某会话最近 N 条消息
5.2 消息相关
插入用户消息
插入 Agent 消息
按 session_id + 时间顺序查询消息
按 task_id 查询某次任务相关消息
查询某消息对应的 artifact 引用
5.3 任务相关
创建任务
更新任务状态
更新任务重试次数
查询任务详情
查询某会话下所有任务
查询失败任务列表
查询某任务的父子关系
5.4 调度与执行相关
创建 agent_run
更新 agent_run 状态
写入 validation 结果
写入 failure 类型
查询某任务的所有 agent run
查询最近失败的 agent run
5.5 Review 相关
写入 review 结果
查询某任务最新 review
统计 review 通过率
查询 review issues
5.6 Artifact 相关
创建 artifact metadata
查询某任务所有 artifact
查询某 artifact 最新版本
查询某会话内所有 artifact
5.7 Replay 相关
插入 replay record
按 task_id 查询 replay timeline
清理超期 replay
清理超量 replay
查询最近 N 条 replay event
5.8 Metrics 相关
写入 metric event
按 task_id 查询指标
按 agent 聚合指标
统计成功率 / retry_count / 平均耗时
查询异常高 retry 的任务
6. 哪些现在可以定，哪些先别定死
现在可以定的
核心实体有哪些
表与表之间的逻辑关系
每类数据需要支持的操作
哪些数据必须结构化
哪些字段必须带 task_id / agent / timestamp
现在不建议完全定死的
主业务数据库一定用 SQLite 还是 Postgres
Metrics 最终是 JSONL、SQLite 还是 Prometheus/OTel
Replay 最终是不是长期都用 SQLite
是否需要 Redis 做状态同步或分布式锁
用户体系、权限体系的完整设计
多租户设计
