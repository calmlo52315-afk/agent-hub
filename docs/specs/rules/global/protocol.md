# Purpose

Define executable system-wide protocol specifications, unified data interaction standards, message structure rules, status definitions, mandatory execution rules and global constraints for full-system module communication and data circulation.

# Scope

Define the applicable boundary of the global protocol, covering all core scenarios and business modules involving cross-module interaction, data transmission, status change and protocol invocation in the system.

- All cross-agent communication in AgentHub MVP
- All Orchestrator-routed message exchanges
- All structured message payload delivery between system modules
- All task status reporting through the unified message protocol

# Responsibilities

Clarify the core rights and obligations of the global protocol, mandatory compliance requirements for all system modules, and the control boundary and execution responsibility of the protocol.

- The system MUST use one structured JSON message protocol for end-to-end communication.
- All modules participating in cross-module interaction MUST comply with the unified message schema.
- All agents MUST encapsulate interaction data in the protocol message body.
- The protocol MUST provide task traceability through `task_id`.
- The protocol MUST provide workflow control through `status`.
- The protocol MUST carry business data through `payload`.
- Raw business data transmission MUST NOT bypass protocol encapsulation.

# Inputs

List all structured input data received by the protocol. Fully reserve all input field descriptions, including data definition, core attributes, required rules and associated constraints.

- `Message`
  - Definition: Global structured JSON message used for full-chain communication
  - Required: Yes
  - Format: JSON object
  - Core attributes:
    - `task_id`
    - `sender`
    - `receiver`
    - `status`
    - `payload`
  - Required rules:
    - The message MUST contain all defined top-level fields.
    - The message MUST be used for all agent-to-agent interaction.
  - Associated constraints:
    - Bare business data MUST NOT be transmitted directly.
    - `payload` content follows the input/output filling rule referenced by `ADR-006`.

# Outputs

List all structured output data generated by the protocol. Fully reserve all output field descriptions, including data definition, producer, data structure and output specifications.

- `Message`
  - Definition: Global structured JSON message emitted after protocol-compliant interaction
  - Producer: Any module or agent participating in protocol-based communication
  - Data structure: Same as the protocol message schema
  - Output specifications:
    - Output MUST remain a structured JSON object.
    - Output MUST preserve all required top-level fields.
    - Output MUST use the defined `status` enumeration.
    - Output MUST carry business content inside `payload`.

# Message Schema

Completely define the core message structure, data hierarchy and overall protocol architecture specifications. Retain all original protocol structure definitions without omission or modification.

```json
{
  "task_id": "string",
  "sender": "string",
  "receiver": "string",
  "status": "string",
  "payload": {}
}
```

- Schema type: Global unique protocol schema
- Data hierarchy: Single top-level JSON object with five required fields
- Architecture role: Unified message envelope for full-chain module communication

# Field Definitions

Standardize and define all fields in protocol input, output, struct and parameters item by item, including field name, data type, required attribute, value range, business explanation and usage scenarios. Keep all complete field details.

- `task_id`
  - Data type: `string`
  - Required: Yes
  - Value range: Globally unique task identifier
  - Business explanation: Used for tracing, replay and statistics across the full chain
  - Usage scenarios: Any protocol message related to a task
- `sender`
  - Data type: `string`
  - Required: Yes
  - Value range: Agent identifier
  - Business explanation: Identifies the message sender
  - Usage scenarios: Any outbound protocol message
- `receiver`
  - Data type: `string`
  - Required: Yes
  - Value range: Agent identifier
  - Business explanation: Identifies the message receiver
  - Usage scenarios: Any routed protocol message
- `status`
  - Data type: `string`
  - Required: Yes
  - Value range:
    - `pending`
    - `running`
    - `success`
    - `failed`
  - Business explanation: Unified status enumeration used to control workflow progression
  - Usage scenarios: Any message that reports execution state or workflow state
- `payload`
  - Data type: `object`
  - Required: Yes
  - Value range: Business payload object
  - Business explanation: Carries actual business data for agent input and output
  - Usage scenarios: Any message carrying task-specific or business-specific content
  - Additional rule: Content MUST be filled according to the input/output specification referenced by `ADR-006`

# Status Definitions

Enumerate all status types involved in protocol operation, data circulation and business execution. Fully retain all status enumeration content, with clear definition of status meaning, trigger conditions, usage scenarios and status transition rules.

- `pending`
  - Meaning: The task or message has been created but execution has not started
  - Trigger conditions: A protocol message is initialized before active processing
  - Usage scenarios: Task creation or queued handoff state
  - Status transition rules: Transition rules beyond enumeration usage are Not Defined
- `running`
  - Meaning: The task or message is under active processing
  - Trigger conditions: A receiving module or agent begins execution
  - Usage scenarios: In-progress business handling
  - Status transition rules: Transition rules beyond enumeration usage are Not Defined
- `success`
  - Meaning: The task or message has completed successfully
  - Trigger conditions: A processing module or agent finishes without failure
  - Usage scenarios: Successful task completion or successful handoff result
  - Status transition rules: Transition rules beyond enumeration usage are Not Defined
- `failed`
  - Meaning: The task or message has completed with failure
  - Trigger conditions: A processing module or agent reaches a failure result
  - Usage scenarios: Error result or unsuccessful task handling
  - Status transition rules: Transition rules beyond enumeration usage are Not Defined

# Workflow

Define the standard business execution flow, data circulation sequence, module interaction logic and mandatory process constraints of the protocol.

- A module or agent MUST create a structured JSON `Message` before sending cross-module data.
- The sender MUST populate `task_id`, `sender`, `receiver`, `status`, and `payload`.
- The sender MUST encapsulate business data inside `payload`.
- The protocol message MUST be used for agent interaction across the full chain.
- The receiving side MUST consume the structured message rather than raw business data.
- Workflow sequencing beyond protocol encapsulation and status-driven flow control is Not Defined in `ADR-011`.

# Rules

Sort out all global mandatory execution rules, interaction rules, invocation rules and data processing rules of the protocol. Retain all business rules completely without omission or simplification.

- The full chain MUST use a unified structured JSON message protocol.
- All agent interactions MUST use this protocol for encapsulation.
- The system MUST NOT use pure string transmission as the communication protocol.
- Business data MUST NOT be transmitted without protocol wrapping.
- `task_id` MUST be passed through the full chain.
- `status` MUST use the unified status enumeration.
- `status` MUST be used to control workflow progression.
- `payload` MUST contain the actual business data.
- `payload` MUST be filled according to the input/output specification referenced by `ADR-006`.
- The protocol definition MUST remain globally unique across the system.

# Runtime Invariants

Define immutable core constraints and underlying runtime standards during protocol execution to ensure unified and stable protocol operation.

- Every protocol message MUST be a structured JSON object.
- Every protocol message MUST contain `task_id`, `sender`, `receiver`, `status`, and `payload`.
- Every protocol message MUST carry a valid `status` value from the defined enumeration.
- Every protocol message MUST carry business content through `payload`.
- Every task-related protocol message MUST preserve the same `task_id` through the full chain.
- Raw business data MUST NOT replace the protocol message body.

# Constraints

Summarize all hard constraints of the protocol, including data constraints, invocation constraints, environment constraints, permission constraints and format constraints. Fully retain all mandatory hard constraint rules.

- Data constraint: Message format MUST be structured JSON.
- Schema constraint: The protocol schema MUST include exactly the defined top-level fields from `ADR-011`.
- Invocation constraint: All agent interactions MUST use protocol encapsulation.
- Format constraint: Pure string communication MUST NOT be used as the protocol form.
- Payload constraint: Actual business data MUST be placed inside `payload`.
- Traceability constraint: `task_id` MUST remain full-chain pass-through data.
- Control constraint: `status` MUST use the defined enumeration and MUST control process flow.
- Dependency constraint: `payload` filling rules depend on `ADR-006`; detailed payload schema is Not Defined in this document.

# Forbidden Actions

Define all prohibited behaviors in protocol operation, module interaction and data processing, as the core basis for system verification and interception.

- Modules MUST NOT send raw business data without protocol encapsulation.
- Modules MUST NOT replace the structured JSON protocol with pure string transmission.
- Modules MUST NOT omit any required top-level field from the protocol message.
- Modules MUST NOT use undefined `status` values outside:
  - `pending`
  - `running`
  - `success`
  - `failed`
- Modules MUST NOT place business payload outside the `payload` field.
- Modules MUST NOT break full-chain `task_id` pass-through.

# Examples

List complete valid and invalid business scenario examples, clearly distinguishing standard compliant operations and non-compliant error operations.

- Valid example:

```json
{
  "task_id": "task-001",
  "sender": "orchestrator",
  "receiver": "coding-agent",
  "status": "pending",
  "payload": {
    "task": "implement feature"
  }
}
```

- Valid example:

```json
{
  "task_id": "task-001",
  "sender": "review-agent",
  "receiver": "orchestrator",
  "status": "success",
  "payload": {
    "review_report": "No blocking issues"
  }
}
```

- Invalid example: raw string transmission

```text
implement feature for task-001
```

- Invalid example: missing required fields

```json
{
  "task_id": "task-001",
  "status": "running",
  "payload": {}
}
```

- Invalid example: undefined status

```json
{
  "task_id": "task-001",
  "sender": "coding-agent",
  "receiver": "review-agent",
  "status": "done",
  "payload": {}
}
```

- Invalid example: business data outside `payload`

```json
{
  "task_id": "task-001",
  "sender": "coding-agent",
  "receiver": "review-agent",
  "status": "success",
  "review_report": "No issues"
}
```
