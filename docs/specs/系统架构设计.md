ADR-001 Runtime 架构选型
决策
MVP 阶段采用 单 Runtime 单体架构；满足触发条件后平滑升级为 Orchestrator + Worker Pool 调度架构。

背景与选择原因
1. 开发周期短（单人/小团队短期交付），单体架构开发、联调、部署成本最低；
2. 当前固定仅 3 个 Agent，角色数量少，无大规模横向扩缩容诉求；
3. 业务以文件级任务为主，单机算力、并发能力完全覆盖场景；
4. 避免过早引入分布式、多进程、网络通信等复杂度，降低现场演示翻车风险。
方案详情
- 当前形态：所有 Agent 运行在同一进程/同一运行时，内存共享、本地方法调用通信；
- 全局资源（文件锁、文件所有权、状态表）全局单例维护。
边界约束
1. 现阶段不设计微服务、多进程、跨主机部署；
2. 所有 Agent 无独立进程/端口，统一由主入口启动。
优缺点
优点
- 开发效率高，调试链路直观；
- 零网络开销，调用延迟极低；
- 单机一键运行，部署简单。
缺点
- 所有 Agent 共享进程资源，无法对单个角色独立扩缩容；
- 进程级别故障会导致全体服务中断；
- 高并发、多角色场景下性能存在上限。
演进触发条件 & 升级路径
触发升级条件（满足任一即启动改造）
1. Agent 角色总数 > 5 个；
2. 业务要求对单个 Worker 独立扩缩容、负载隔离；
3. 单进程并发压力达到性能瓶颈。
演进路径
单 Runtime → 解耦为 Orchestrator（独立调度中心） + Worker Pool（工作节点池）
- Orchestrator：仅负责任务拆解、路由、资源管控、流程流转；
- 原有业务逻辑全部下沉为独立 Worker；
- 通信改为统一消息协议，保留原有业务代码 100% 复用。

ADR-002 Agent 数量 & 职责边界
决策
MVP 固定使用 3 个核心 Agent：Coding / Review / Artifact；编码细分角色作为扩展可选模块，不作为主流程。
严格定义权责清单 + 禁止行为，杜绝职责串台。

背景与选择原因
1. 三角色分工贴合代码协作全链路，流程短、稳定性强，适配竞赛演示；
2. 角色越少，状态同步、冲突、上下文问题越少，可控性越高；
3. 预留扩展接口，后续可按需拆分细分领域 Agent。
方案详情 & 权责边界
1. Coding Agent
拥有能力
- 需求理解、代码任务规划
- 业务代码生成、变更 Diff 生成
- 单元测试代码生成
- 代码自检
禁止行为（强约束）
- 禁止执行代码审核、质量打分
- 禁止修改全局规则、文件规范、接口契约
- 禁止篡改任务原始需求与规格文档
2. Review Agent
拥有能力
- 代码语法、逻辑、风格、接口合规性审查
- 问题识别、问题归类、风险等级评定
- 质量评分、输出修复建议、冲突合并处理
禁止行为（强约束）
- 禁止直接新增/重构业务代码（仅允许微小格式修正）
- 禁止分配任务、修改文件所有权与锁状态
3. Artifact Agent
拥有能力
- 全量产物收集、完整性校验
- 文件快照、版本归档、元数据生成
- 预览卡片生成、工程打包输出
禁止行为（强约束）
- 禁止生成、修改业务代码与单测
- 禁止介入代码评审与风险判定
边界约束
1. 所有 Agent 遵循「单一职责」，跨角色操作必须经由 Orchestrator 中转；
2. 新增细分角色（Frontend/Backend/DB/Test）仅作为可选扩展，不侵入主流程。
优缺点
优点：边界清晰、流程闭环、调试简单、演示稳定。
缺点：编码能力聚合，单 Coding Agent 承载多技术栈，专业性粒度较粗。

演进路径
当业务需要精细化分工时，从 Coding Agent 拆分出前端、后端、数据库、测试等专用 Worker；Review、Artifact 保持全局唯一不拆分。

ADR-003 文件所有权 & 冲突策略
决策
全局采用 one_file_one_owner 单文件单归属原则，结合目录级所有权绑定 + 文件锁机制，从源头杜绝跨主体篡改。

背景与选择原因
1. 代码冲突核心根源为多主体同时修改同一文件；目录+文件绑定可从分配阶段拦截风险；
2. 明确只读/读写权限，统一规则，AI/开发不会出现越权修改。
方案详情（目录所有权配置）
# 文件所有权配置
ownership_rules:
  coding_frontend:
    write:
      - frontend/**
    read: all
  coding_backend:
    write:
      - gateway/**
      - runtime/**
    read: all
  coding_db:
    write:
      - db/**
      - sql/**
    read: all
  review_agent:
    write: []       # 只读权限
    read: all
  artifact_agent:
    write:
      - workspace/**/artifacts/
      - workspace/**/preview/
    read: all

冲突处理策略
1. 事前规避：Orchestrator 分配任务前校验所有权，非归属 Agent 直接拒绝分配；
2. 运行防护：搭配全局文件锁，已占用文件禁止二次写入；
3. 事后处置：出现非归属修改 → 判定为违规操作，自动回滚并记录告警。
边界约束
1. 一个文件/目录仅绑定一个可写主体；
2. Review、Artifact 类角色默认全局只读，仅允许操作产物目录；
3. 禁止手动修改所有权配置，变更需统一走配置文件更新。
演进路径
复杂项目可补充代码块级行号锁，支持单文件内多区域并行编辑。

ADR-004 产物存储规范
决策
采用 按任务隔离的分层目录结构 存储所有产物，统一目录范式，避免文件混乱。

背景与选择原因
1. 多轮任务、多版本文件混杂会导致溯源、回放、产物整理困难；
2. 分层目录区分源码、编译产物、预览资源，结构标准化，便于 Artifact Agent 解析。
目录规范（强制标准）
workspace/
  ├─ task_001/          # 按任务ID隔离根目录
  │  ├─ source/         # 原始代码、源码文件
  │  ├─ artifacts/      # 编译产物、单元测试、变更Diff
  │  └─ preview/        # 预览卡片、元数据、报告文件
  ├─ task_002/
  └─ ...

边界约束
1. 所有任务文件必须归入对应 task 目录，禁止散落在根路径；
2. 不同类型文件严格归入对应子目录，不得跨目录存放。
演进路径
后期增加定时清理策略、冷热数据分离、远程对象存储对接。

ADR-005 上下文（Context）管理策略
决策
定义上下文优先级 + 裁剪规则，明确 Token 不足时的淘汰顺序，保障核心信息不丢失。

背景与选择原因
长流程下上下文溢出、信息丢失是高频问题；必须提前约定优先级与裁剪逻辑，Prompt 与代码才有统一依据。

基础配置
context_config:
  recent_messages: 10
  pinned_messages: all
  artifact_summary: 3

上下文优先级（从高到低，高优先级最后裁剪）
priority:
  1: pinned_messages    # 固定规则、全局约束、原始需求（永久保留）
  2: active_task        # 当前执行任务、文件信息、锁状态（核心运行数据）
  3: artifact_summary   # 产物摘要、评审结论（业务结果）
  4: recent_messages    # 历史交互、过往日志（最先裁剪）

裁剪规则
1. Token 达到阈值时，从最低优先级开始逐步裁剪；
2. pinned_messages 全局固定，永不裁剪；
3. 单轮上下文保留当前任务完整链路，不截断活跃任务信息。
边界约束
禁止打乱优先级顺序做随机裁剪。

演进路径
后期接入独立向量记忆、阶段摘要、RAG 按需检索，彻底弱化上下文窗口限制。

ADR-006 Agent 思维链 & 输入输出规范
决策
各 Agent 使用领域定制化线性思维链；统一标准化输入/输出结构，形成可复用 agent-spec。
顶层 Orchestrator 采用 Plan-and-Execute 范式，内外范式分层解耦。

背景与选择原因
1. 业务专属步骤链更贴合编码评审场景，稳定性、演示效果优于通用 ReAct；
2. 标准化出入参，上下游解析零歧义，适配自动化流转。
一、各 Agent 思维链路（最终版）
Coding Agent
1. 需求理解 & 上下文加载
2. 任务规划
3. 代码生成
4. 自我审查 & 缺陷自检
5. 单元测试生成
6. 变更 Diff 生成
7. 结果上报
Review Agent
1. 产物加载 & 冲突合并检测
2. 全维度代码审查
3. 问题识别 & 归类
4. 风险评级（高/中/低）
5. 分级处置 + 修复建议
6. 评审报告输出
Artifact Agent
1. 产物收集 & 完整性校验
2. 文件快照 & 版本归档
3. 元数据生成
4. 预览卡片生成
5. 最终工程打包输出
二、标准化输入输出（YAML 规范）
Coding Agent
input:
  - 任务基础信息 task
  - 全局上下文 context
output:
  - 业务代码 code
  - 变更差异 diff
  - 单元测试 unit_test

Review Agent
input:
  - 原始代码 code
  - 变更记录 diff
output:
  - 质量评分 score
  - 问题列表 issues
  - 修复建议 suggestions

Artifact Agent
input:
  - 评审后全量产物
output:
  - 归档文件包
  - 元数据 metadata
  - 预览卡片 preview_card

边界约束
1. 思维链禁止跳步、逆序执行；
2. 输出严格按照约定字段返回，自由文本仅作为补充描述。
演进路径
单步骤可嵌套小型 ReAct 循环做精细化推理；整体主链路保持线性不变。

ADR-007 Task 任务粒度规范
决策
严格限制任务粒度，禁止超大任务，确保 Orchestrator 可正常拆解、Agent 可稳定执行。

背景与选择原因
任务过大易导致理解偏差、上下文过载、执行超时，必须提前划定上下限。

允许粒度（示例）
- 开发登录页面
- 开发 Todo 业务接口
- 审核指定模块代码
- 生成指定文件单测
禁止粒度（强约束）
- 开发整套系统
- 一次性完成全项目重构
- 跨数十个文件的无边界超大任务
边界约束
1. 单个任务原则上对应 ≤3 个物理文件；
2. 超大需求由 Orchestrator 强制拆分为多个细粒度子任务串行执行。
演进路径
后续增加任务自动拆分算法，支持复杂需求智能拆解。

ADR-008 任务回放（Replay）存储策略
决策
使用 SQLite 轻量化数据库存储回放日志，约定容量与生命周期，防止数据无限膨胀。

方案配置
replay_config:
  storage_engine: SQLite
  retain_days: 30        # 数据保留时长
  max_records: 5000      # 最大存储条数

边界约束
1. 达到条数上限/时长上限，自动按时间淘汰旧数据；
2. 回放数据仅用于调试、复盘、演示，不参与业务主流程。
演进路径
高并发场景迁移至时序数据库，增加日志检索、筛选、回放重跑能力。

ADR-009 指标监控（Metrics）定义
决策
统一监控指标项，用于质量统计、性能分析、效果评估。

监控指标清单（强制采集）
metrics:
  - task_success_rate    # 任务成功率
  - retry_count          # 全局重试次数
  - review_pass_rate     # 代码评审通过率
  - token_usage          # Token 消耗量
  - avg_response_time    # 平均响应耗时

边界约束
所有指标按任务 ID、Agent 维度做维度拆分统计。

演进路径
后续增加告警阈值、可视化大盘、异常指标告警。

ADR-010 模型路由策略
决策
模型选型暂不硬编码指定，仅定义选型原则，根据实际可用模型动态适配。

选型原则（核心规则）
1. Coding Agent：优先选择代码生成能力最强的大模型；
2. Review Agent：优先选择逻辑推理、语义理解能力最强的大模型；
3. Artifact Agent：优先选择调用成本低、响应快的模型。
边界约束
模型切换不改动业务流程、输入输出格式。

演进路径
后续落地模型负载均衡、自动降级、多模型混合路由。

ADR-011 Agent 通信协议（核心）
决策
全链路统一使用 结构化 JSON 消息协议，废弃纯字符串传递，保证跨角色、跨架构兼容。

背景与选择原因
纯字符串通信无字段、无状态、无法自动化解析；结构化协议是多 Agent 协作、后续架构升级的基础。

标准消息体（全局唯一协议）
{
  "task_id": "string",       // 全局唯一任务ID
  "sender": "string",        // 发送方Agent标识
  "receiver": "string",      // 接收方Agent标识
  "status": "string",        // 状态：pending/running/success/failed
  "payload": {}              // 业务载荷（对应各Agent出入参）
}

字段说明
- task_id：全链路透传，用于追踪、回放、统计；
- status：统一状态枚举，控制流程流转；
- payload：承载实际业务数据，按 ADR-006 出入参规范填充。
边界约束
1. 所有 Agent 间交互必须使用该协议封装；
2. 禁止直接裸传业务数据。
演进路径
架构升级为 Worker Pool 后，协议完全复用，仅增加消息队列转发层。
