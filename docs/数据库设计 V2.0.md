# 数据库设计 V2.0 — PostgreSQL 统一存储

## 1. 设计目标

本次 V2.0 是 V1.0 的落地升级版，核心变化是 **从"逻辑模型先行、物理存储后定"推进到"选型确定、表结构定稿"**。

具体目标：

- **Gateway Store + Replay Store 二合一**：原来 Gateway 的 SQLite (`gateway.db`) 和 Runtime 的 Replay SQLite (`replay.db`) 是两个独立 SQLite 文件，通过各自代码独立建表、独立迁移。本次统一为单 PostgreSQL 实例，一套 schema 管理。
- **为幂等、DAG、预算统计提供稳定存储基座**：不再每次补功能时反复补存储层。
- **保留 V1.0 全部核心实体设计**：V1.0 的 11 张逻辑表全部在本版本落地为物理表。
- **兼容当前代码接口**：Gateway 的 `store.Backend` interface 和 Runtime 的 `SQLiteReplayStore` 调用模式可以平滑切换。

## 2. 从 V1.0 到 V2.0 的核心变化

| 维度 | V1.0 | V2.0 |
|------|------|------|
| 数据库 | "PostgreSQL 优先，早期可临时用 SQLite" | **确定 PostgreSQL** |
| Gateway 存储 | SQLite `gateway.db`（8 张表） | 迁移到 PostgreSQL，接口不变 |
| Replay 存储 | SQLite `replay.db`（1 张宽表） | 合并进 PostgreSQL 统一 events 表 |
| Metrics 存储 | JSONL 文件 | 迁移到 PostgreSQL metric_events 表 |
| 事件模型 | Gateway session_events + Replay replay_records 两套 | **统一 events 表** |
| 幂等支持 | 无 | 新增 idempotency_keys + skill_invocations |
| DAG 支持 | 仅 task_dependencies 概念 | 新增 task_dependencies 物理表 |
| 预算统计 | 仅配置文件 | 新增 cost_records（可查询、可聚合） |

## 3. 架构决策

### 3.1 为什么是 PostgreSQL 而不是继续用 SQLite

1. **并发写入**：Gateway 的 WebSocket 事件写入和 Runtime 的 Replay 事件写入会同时发生。SQLite 单写锁会成为瓶颈。
2. **JSONB 支持**：大量半结构化数据（payload、card_json、issues_json）需要 JSONB 的索引和查询能力。
3. **迁移工具链成熟**：`golang-migrate` + `alembic` 都可以管理 PostgreSQL schema。
4. **Docker Compose 一键部署**：加一个 `postgres` 服务即可，不增加运维复杂度。
5. **后续扩展**：Redis 缓存、读写分离、连接池都是 PostgreSQL 生态的标准操作。

### 3.2 什么不进 PostgreSQL

| 数据类型 | 存储位置 | 理由 |
|----------|----------|------|
| Artifact 大文件（代码、diff、预览产物） | 文件系统 / 对象存储 | V1.0 原则不变：结构化元数据入库，原始大文件走文件系统 |
| 运行时锁状态 | 内存 | 锁的生命周期是毫秒-秒级，不需要持久化 |
| 状态机临时态 | 内存 | transition 事件写入 events 表即可，当前状态在 tasks.status 中 |
| 上下文窗口 | 内存 | 生命周期仅限单次 Agent 调用 |
| 预算配置 | `execution-rules.json` | 配置属于规则层，不混入业务数据 |

## 4. 表设计

### 设计约定

- **主键**：业务实体用 `UUID`（`gen_random_uuid()`），事件/指标用 `BIGSERIAL`
- **时间戳**：统一 `TIMESTAMPTZ`，存储 UTC，应用层负责时区转换
- **JSON 字段**：统一 `JSONB`，不用 `TEXT` 存 JSON 字符串
- **外键**：核心实体间加 FK，事件表因性能考虑不加 FK 约束（仅逻辑关联）
- **命名**：snake_case，表名复数

### A9. events（核心：统一 Gateway 事件 + Replay 记录）

这是本次存储统一最关键的表。替换：
- Gateway 的 `session_events`（seq + event_json）
- Runtime 的 `replay_records`（20+ 列的宽表）

设计思路：**不保留 `event_json` 或 `payload_json` 大 JSON 列作为唯一数据载体，而是把可查询的维度拆成列，剩余动态数据放 JSONB。**

```sql
CREATE TABLE events (
    id           BIGSERIAL PRIMARY KEY,
    session_id   UUID NOT NULL,              -- 逻辑 FK → sessions，不加约束以优化写入
    task_id      UUID,                       -- 逻辑 FK → tasks，可为空
    trace_id     TEXT NOT NULL DEFAULT '',
    seq          BIGINT NOT NULL,            -- 会话内递增序号，WebSocket 同步依赖
    event_type   TEXT NOT NULL,              -- 事件类型目录见 §6
    role         TEXT NOT NULL DEFAULT '',   -- user|system|agent（message 类事件用）
    agent_name   TEXT NOT NULL DEFAULT '',   -- 消息/事件的来源 Agent
    payload      JSONB NOT NULL DEFAULT '{}', -- 完整事件负载
    metadata     JSONB NOT NULL DEFAULT '{}', -- 扩展属性（sender/receiver/in_reply_to 等）
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 按会话 + seq 拉取增量事件（WebSocket 同步，最频繁）
CREATE UNIQUE INDEX idx_events_session_seq ON events (session_id, seq);

-- 按任务查时间线（Replay 核心查询）
CREATE INDEX idx_events_task_time ON events (task_id, created_at, id)
    WHERE task_id IS NOT NULL;

-- 按事件类型 + 时间（skill 粒度查询、指标聚合）
CREATE INDEX idx_events_type_time ON events (event_type, created_at, id);

-- 按 trace_id 查询全链路事件
CREATE INDEX idx_events_trace ON events (trace_id, created_at)
    WHERE trace_id != '';
```

**字段来源映射**：

| events 列 | Gateway session_events 来源 | Replay replay_records 来源 |
|-----------|---------------------------|--------------------------|
| session_id | session_id | 从 message envelope 中提取 |
| task_id | 从 event.SessionID 或 payload 提取 | task_id |
| trace_id | 从 event 提取 | trace_id |
| seq | seq（自增） | 新分配的全局 seq |
| event_type | 从 event.Type 映射 | record_type + event_type 映射 |
| role | 从 event 推断 | sender_type 映射 |
| agent_name | 从 event 推断 | sender_id |
| payload | event_json 原文 | payload_json 原文 |
| metadata | — | {sender, receiver, in_reply_to, message_id, msg_kind, msg_status} |
| created_at | created_at | timestamp |

#### B1. task_dependencies

V1.0 §4.4 落地。支持子任务 DAG 调度（ADR-007 + dag-execution-spec）。

```sql
CREATE TABLE task_dependencies (
```

#### B2. agent_runs

V1.0 §4.5 落地。区分 task 和 agent_run，精确记录每次 retry/fallback。

```sql
CREATE TABLE agent_runs (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    task_id             UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    agent_name          TEXT NOT NULL,
    run_index           INTEGER NOT NULL DEFAULT 1,
    status              TEXT NOT NULL DEFAULT 'pending',  -- pending|running|success|failed|retrying
    input_payload       JSONB NOT NULL DEFAULT '{}',
    output_payload      JSONB NOT NULL DEFAULT '{}',
    validation_passed   BOOLEAN,

    failure_category    TEXT NOT NULL DEFAULT '',  -- system_error|model_error|validation_error|file_lock_error|timeout_error
    started_at          TIMESTAMPTZ,
    finished_at         TIMESTAMPTZ,
    latency_ms          INTEGER NOT NULL DEFAULT 0,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 查询某任务的所有执行记录
CREATE INDEX idx_agent_runs_task ON agent_runs (task_id, run_index);
-- 查询最近失败的 agent run
CREATE INDEX idx_agent_runs_failed ON agent_runs (status, finished_at DESC)
```


#### B4. idempotency_keys（幂等基座）

为 Skill 幂等（todo.md §Skill 幂等）和 stage-7 的幂等能力建设提供存储。

```sql
CREATE TABLE idempotency_keys (
    key             TEXT PRIMARY KEY,              -- idempotency_key（客户端生成或 hash 生成）
    invocation_id   TEXT UNIQUE NOT NULL,          -- invocation_id（服务端生成 UUID）
    task_id         UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    skill_name      TEXT NOT NULL DEFAULT '',
    status          TEXT NOT NULL DEFAULT 'pending',  -- pending|completed|failed
    result_json     JSONB NOT NULL DEFAULT '{}',   -- 缓存的结果，重复调用直接返回
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at      TIMESTAMPTZ NOT NULL           -- 过期清理
);

CREATE INDEX idx_idempotency_expires ON idempotency_keys (expires_at)
    WHERE status IN ('completed', 'failed');
```

**使用模式**：
1. 调用方生成 `idempotency_key`（或由服务端根据 `task_id + skill_name + input_hash` 生成）
2. `INSERT INTO idempotency_keys` — 如果 key 冲突（重复调用），直接返回 `result_json`
3. 执行完成后 `UPDATE SET status='completed', result_json=$result`
4. 定时任务清理 `expires_at < NOW()` 的记录

## 5. 索引策略总览

按访问频率从高到低：

| 查询场景 | 索引 | 频率 |
|----------|------|------|
| WebSocket 增量同步事件 | `idx_events_session_seq (session_id, seq)` UNIQUE | 极高 |
| 会话列表（按用户） | `idx_sessions_owner_updated (owner_id, updated_at DESC)` | 高 |
| 会话内任务列表 | `idx_tasks_session_status (session_id, status, updated_at DESC)` | 高 |
| 任务时间线（Replay） | `idx_events_task_time (task_id, created_at, id)` | 高 |

## 7. 迁移策略

### 7.1 迁移分 3 步

```
Step 1: 建 PostgreSQL schema
  ├─ 执行本设计的 CREATE TABLE 语句
  ├─ 验证 Gateway 和 Runtime 都能连接 PostgreSQL
  └─ 不影响现有 SQLite 运行

Step 2: 双写过渡（可选，降低风险）
  ├─ Gateway: 同时写 SQLite + PostgreSQL
  ├─ Runtime: 同时写 Replay SQLite + PostgreSQL events
  └─ 验证数据一致性后切读

Step 3: 切换为单写 PostgreSQL
  ├─ Gateway: GATEWAY_STORE_BACKEND=postgres
  ├─ Runtime: REPLAY_STORE_BACKEND=postgres
  ├─ 移除 SQLite 文件
  └─ 清理过渡代码
```

### 8.1 获取会话最近 50 条消息（Chat UI）

```sql
SELECT id, seq, event_type, role, agent_name, payload, created_at
FROM events
WHERE session_id = $1
  AND event_type LIKE 'message.%'
  AND seq > $2  -- after_seq
```

```sql
SELECT id, event_type, agent_name, payload, created_at
FROM events
WHERE task_id = $1
ORDER BY created_at ASC, id ASC;
```

### 8.3 统计任务成功率（Metrics）

```sql
SELECT
    agent,
    COUNT(*) FILTER (WHERE metric = 'task_success_rate' AND value = 1) AS success_count,
    COUNT(*) FILTER (WHERE metric = 'task_success_rate') AS total_count,
    ROUND(100.0 * COUNT(*) FILTER (WHERE metric = 'task_success_rate' AND value = 1)
        / NULLIF(COUNT(*) FILTER (WHERE metric = 'task_success_rate'), 0), 2) AS success_rate
FROM metric_events
WHERE created_at > NOW() - INTERVAL '7 days'
GROUP BY agent;
```

### 8.4 幂等检查（Skill 调用前）

```sql
-- 尝试插入幂等键，如果冲突则返回已有结果

    -- 如果已完成，不做任何事（通过 RETURNING 判断）
    status = idempotency_keys.status
RETURNING status, result_json;
```

```sql
JOIN task_dependencies d ON d.task_id = t.id
```

## 附录：为什么 events 表不拆成 messages + replay_events 两张表

有人可能倾向于把 messages（聊天消息）和 replay_events（系统事件）分开存储。这里记录不拆的理由：

1. **统一时序**：在一次任务执行中，用户消息、Agent 输出、状态转移事件是交错发生的。把它们放在一张表里，按 `created_at` 排序就能得到完整时间线。
2. **Replay 需求**：Replay 既需要展示消息（"用户说了什么"），也需要展示事件（"系统做了什么决策"）。分开存储意味着 Replay 查询要做 UNION + SORT，反而更复杂。
3. **event_type 区分**：通过 `event_type` 列（`message.*` vs `task.*` vs `skill.*`）可以轻松过滤。Chat UI 只查 `message.%`，Debug 面板查全部。
4. **索引不会浪费**：`idx_events_session_seq` 已经覆盖了按会话拉消息的场景。如果拆表，反而需要维护两个索引。
5. **JSONB 足够灵活**：`payload` 列承载了不同类型事件的差异化字段，不需要为每种事件类型单独建表。
